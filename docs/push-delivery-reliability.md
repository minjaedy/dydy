# 일정 알림 반복 발송 수정 · 2026-10-22

## 확인한 원인

운영 Worker tail에서 분 단위 예약 작업의 `exceededCpu` 종료를 확인했다. 기존 전송 코드는 기기별 레코드를 `sending`으로 만든 다음 푸시를 보내고 마지막에 `sent`를 기록했다. 전송 도중 또는 전송 후 저장 전에 Worker가 중단되면, 2분 뒤 같은 레코드를 다시 전송했다. 실제 일정 알림에도 완료 기록 없이 lease만 갱신되는 레코드가 있었다. 기기 endpoint의 중복 등록은 없었다.

## 변경

- 기기 + 알림 키의 기존 SHA-256 식별자를 유지한다. 일정 등록, 당일, 기념일 전날, 1시간 전은 서로 다른 알림이다.
- 암호화 준비 단계인 `sending`만 lease 만료 후 다시 시도할 수 있다.
- 외부 전송 **직전** `dispatching`을 영속 저장한다. 전송 성공 후에는 `sent`, 전송 결과가 불확실한 timeout/저장 실패에는 `uncertain`을 남긴다. `dispatching`과 `uncertain`은 만료 후에도 자동 재전송하지 않는다.
- 제공업체가 명시적으로 거절한 응답과 준비 단계 실패는 `failed`로 저장하고 1분 후 재시도한다. 404/410은 해당 구독만 해제한다. 실패한 기기가 다른 기기로의 발송을 막지 않는다.
- 전송 직전에 읽음 상태와 lease 소유권을 다시 확인한다. 읽음 처리와 다른 사용자 알림에는 영향을 주지 않는다.
- Web Push 암호화와 서버 OAuth 서명을 비동기 Web Crypto로 처리한다. 기존 VAPID 키를 유지하고 서명 캐시/동시 OAuth 갱신 합치기로 중복 계산을 줄인다.
- 매 스캔에서 완료된 전송 기록과 기기를 한 번 불러온다. 변경 없는 채팅 일정 카드 재저장과 중복 정리 작업을 생략한다. 정리 주기는 시간당 1회이며 성공/실패/불확실 전송 기록의 보관 기간은 기존 7일이다.

전송 제공업체와 D1 사이에는 원자적 트랜잭션이 없으므로, 중단 시 정확히 한 번의 단말 도착을 보장할 수는 없다. `dispatching`/`uncertain`은 **수신 확인**을 뜻하지 않는다. 불확실한 결과를 재발송해 같은 알림을 계속 울리는 대신, 앱의 알림함을 유지한다. 근거 없이 이 상태를 `failed`로 초기화하거나 삭제하면 같은 알림이 다시 전송될 수 있다.

## 검증과 운영 적용

- 동시 스캔, 전송 후 DB 실패, hard termination 잔여 상태, timeout, 제공업체 거절 및 재시도, 구독 만료, 사용자/기기 분리, 전송 중 읽음 처리를 자동 테스트한다.
- 생성한 Web Push 메시지를 독립된 `http_ece` 구현으로 복호화하고, VAPID/RSA 서명을 별도 검증한다. 검증 키는 테스트 중 생성하며 운영 구독에 테스트 메시지를 보내지 않는다.
- 기존 알림·인증·읽음·채팅·자동 정리 테스트를 함께 실행한다.
- Worker 배포 후 `/health` 정상 응답과 예약 작업 `outcome: ok`, 예외 없음, 해제된 sync lease를 확인했다. 배포 시점에 남은 이전 방식의 불확실한 전송 1건만 자동 재전송하지 않도록 격리했다. 사용자 알림함과 읽음 상태는 변경하지 않았다.
- 실제 휴대폰 도착 여부는 이 점검에서 별도 시험하지 않았다. 새 데이터베이스 열이나 키 교체, 앱 재설치는 필요 없다.

표준: [RFC 8291](https://www.rfc-editor.org/rfc/rfc8291), [RFC 8292](https://www.rfc-editor.org/rfc/rfc8292). 운영 제한: [Cloudflare Workers limits](https://developers.cloudflare.com/workers/platform/limits/).
